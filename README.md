# NAVI / FaZe CS2 monitor

Український мобільний дашборд NAVI та FaZe: матчі сезону 2026, склад, новини й зведення з посиланнями. Час — `Europe/Berlin`.

## Надійність даних

- Основне джерело за замовчуванням — bo3.gg: матчі, карти, склад і доступна статистика гравців. `MATCH_SOURCE=liquipedia` залишає альтернативний шлях через Liquipedia. Записи різних джерел зберігаються, але не підсумовуються разом у статистиці сезону.
- Liquipedia також постачає посилання на публічні Telegram-канали. Її запити розділені щонайменше двома секундами; запити обох джерел мають таймаут і сторінкове завантаження історії.
- Відсутність запису у відповіді **не видаляє історію і не означає скасування**. Зниклий незавершений матч залишається в розділі записів для уточнення. Неповна відповідь не стирає відомий результат чи карти.
- Статуси: заплановано, триває, завершено, перенесено, скасовано, невідомо. Невідомий результат не стає нічиєю. Технічні результати не входять у форму прогнозу. Суперечність переможця та рахунку позначається окремо.
- Склад оновлюється лише після перевірки повноти (5–10 гравців, без дубльованих ID). Це захист від неповного парсингу, а не офіційне підтвердження трансферу.
- Опційний `PANDASCORE_TOKEN` підключає незалежну звірку розкладу, статусу, формату й рахунку. Неоднозначні повторні зустрічі не підтверджуються автоматично. Суперечності показуються; друге джерело не перезаписує перше. Це незалежний постачальник даних, не офіційний організатор турніру.
- Без другого джерела інтерфейс показує «Одне джерело». Склад поки не має другого офіційного підтвердження.
- Кожна команда має окремі перевірки матчів, складу та новин: остання спроба, останній успіх, помилка та зауваження. Збій новин не блокує результати; збій NAVI не блокує FaZe. Пропуск двох інтервалів позначає дані застарілими.

## Новини і зведення

NAVI: CS2 JSON-стрічка `navi.gg`. FaZe: офіційна Atom-стрічка `https://fazeclan.com/blogs/news.atom`. Вона може не мати новин CS2; відсутність покриття показується явно. Telegram — лише канали, на які посилаються сторінки клубу й активних гравців у Liquipedia. Тематика фільтрується за термінами CS2 та ніками; фільтр може пропускати неоднозначні дописи. X та Instagram не підключені.

Дублікати прибираються за URL і нормалізованим текстом. Один допис може належати обом командам без перезаписування прив'язки. Тон визначається словником і не є оцінкою психологічного стану людини.

Фактичне українське зведення працює без AI-ключа. Кожне твердження має джерело й час перевірки. Якщо задані `OPENAI_API_KEY` та `OPENAI_MODEL`, Responses API обирає й упорядковує до шести вже сформованих фактів. Відповідь перевіряється за дозволеними ID; AI не може додати в інтерфейс власні твердження чи URL. Результат кешується за змістом, модель не викликається при перегляді сторінки. Збій API залишає фактичне зведення.

Документація інтеграцій: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [PandaScore CS matches](https://developers.pandascore.co/reference/get_csgo_matches_upcoming-1).

## Прогнози

Відсотки перемоги й третьої карти приховані: точність моделей не підтверджена. Опис матчу bo3.gg розділяє недавні зустрічі, спільних суперників, форму гравців і особисті зустрічі. Рейтинг bo3 має шестимісячне вікно; K/D та ADR використовують доступне вікно статистики. Ретроспективний аудит відрізняє збережені оцінки від повторного розрахунку.

Альтернативна модель Liquipedia порівнює однакове вікно 90 днів, до 10 останніх серій кожної команди. Мінімум — п'ять придатних матчів на сторону; невідомі й технічні результати виключаються. За відомого нового складу вибірка обрізається до відповідних матчів. Майбутні результати виключаються з розрахунку.

`npm run backtest -- --since=2026-07-01` завантажує історію Liquipedia й запускає послідовну ретроспективну перевірку. Файли `reports/history.json` та `reports/backtest.json` містять вхідні дані, Brier score (менше — краще), базу 0.25 для прогнозу 50/50, покриття та калібрувальні групи. Повтор без мережі: `npm run backtest -- --input=reports/history.json`.

Для захисту від використання ще незавершених матчів тест має 24-годинний відступ. Це тест на поточній виправленій історії, а не на архівних знімках джерела. Історична відомість складу не відновлюється; сила суперників, veto, travel та stand-in поки не моделюються. Звіт **не вмикає відсотки автоматично**. Часті вибірки недостатніх даних й невдалий результат тесту не приховуються.

## Локальний запуск

Потрібні Node.js 22+ і PostgreSQL. Тести використовують ізольований вбудований PostgreSQL через PGlite і не потребують робочої бази.

```powershell
npm ci
Copy-Item .env.example .env
# Налаштуй DATABASE_URL і CRON_SECRET у .env.
npm test
npm run typecheck
npm run check:sources # живі джерела, запис лише в ізольовану тестову базу
npm run sync -- --force
npm run dev
```

Фоновий процес моніторингу в окремому терміналі:

```powershell
npm run sync:watch
```

Він перевіряє, які оновлення потрібні: матчі кожні 15 хвилин, новини щогодини, склад раз на 6 годин. Після помилки — повтор не частіше ніж раз на дві хвилини. Кнопка «Оновити» запускає всі перевірки примусово. Дві одночасні синхронізації розділені advisory lock PostgreSQL. Процес `sync:watch` має постійно працювати для локального автоматичного моніторингу; сам вебсервер його не запускає.

Сторінки NAVI: `/`, `/matches`, `/players`, `/pulse`; FaZe — ті самі шляхи з префіксом `/faze`.

## Розгортання

`vercel.json` містить сумісний із Vercel Hobby cron `0 5 * * *` для `/api/sync`: раз на добу, о 05:00 UTC. Інтервали 15 хвилин / година / 6 годин застосовуються лише за частого запуску перевірок, наприклад у власному постійному Node-процесі `npm run sync:watch`. Для 15-хвилинного cron у Vercel потрібен план, що підтримує таку частоту; щоденний cron не забезпечує 15-хвилинної свіжості. Конфігурація у репозиторії сама по собі не запускає моніторинг у хмарі.

На сервері встанови `DATABASE_URL` і `CRON_SECRET`, опційно `PANDASCORE_TOKEN`, `OPENAI_API_KEY`, `OPENAI_MODEL`. Секрети залишаються на сервері. Cron надсилає `Authorization: Bearer <CRON_SECRET>`. Ендпоінт повертає 207 для часткового оновлення; подробиці зберігаються у `source_checks` та `sync_runs`.

Схема мігрується автоматично без видалення таблиць. Жодні Rating, ADR, KAST або K/D без даних джерела не генеруються.
